# AI 趣味测评矩阵运营手册

更新日期：2026-07-15

## 1. 商业模型

唯一主商品：`AI 趣味测试完整报告兑换码`。

- 售价：1.9 元。
- 一码仅首次激活一次。
- 首次激活后，同一浏览器可查看 15 项测评的深度报告。
- 跨子域共享 Cookie 当前最长保存 365 天；浏览器策略或用户清理数据可能使它提前失效。
- 免费层负责传播：主结果、核心分数、一段解释、3 个标签、结果分享卡。
- 付费层按测试适用提供答案证据、维度拆解、盲区、触发场景、沟通话术等内容；统一最低交付是结果依据、维度解读和可执行建议。
- 不拆成 15 种卡，不新增复杂会员或账号体系。

用户不是为“多看几段形容词”付费，而是为“为什么会得到这个结果，以及接下来能怎么做”付费。

## 2. 产品分组与导流

### 流量入口

- `trusttest`：一屏选 3 个，评论分歧强，作为首要内容入口。
- `last8test`：3 秒读懂的低电量情境，适合截图、投票和复测。
- `restarttest`：非恋爱泛人群入口，扩大万能卡受众。
- `citytest`：题材宽、容易晒城市卡，承担泛人群拉新。
- `cptest`：情侣和朋友都能参与，承担互测传播。
- `bftest`：考试感强，适合评论区讨论和转发给对象。
- `eletest`：社交电量门槛低，适合非恋爱用户。

### 购买转化

- `lovetest`：上头触发器、自我边界和降温清单。
- `lswtest`：关系靠近方式、触发循环和沟通模板。
- `lvtest`：亲密状态、错频点和修复任务。
- `emotest`：内耗触发器、停止复盘和恢复动作。

### 使用与复测

- `gftest`：恋爱主型与压力下副人格。
- `mstest`：外在模式和隐藏表达欲。
- `shiptest`：关系信号接收偏差，避免判断他人真实意图。
- `ggtest`：友情分工、边界和冲突修复。

导流原则：结果页默认只推荐 4 项最相关测试，允许用户展开其余 14 项；不要一次平铺全部项目制造选择过载。

## 3. 爆款内容结构

每条小红书笔记只完成一个任务：让用户停留、评论或进入商品页，不要同时塞满所有卖点。

推荐首图结构：

1. 一个 3 秒能看懂的高压假设。
2. 4—8 个有分歧但无明显正确答案的选项。
3. 一句评论钩子，例如“你会先排除谁？”或“只能留 3 个，你选哪组？”
4. 第二张图再解释它对应的测评主题。
5. 商品链接承接完整版，不在评论区承诺“保证准确”。

题目语言采用 `70/20/10`：

- 70% 长期有效的生活场景。
- 20% 当年社交语境，例如群聊、已读不回、临时改计划、搭子关系。
- 10% 网络梗和荒诞题，用来制造记忆点。

结果卡采用：`短码 + 中文人格名 + 一句判词 + 一个反差点`。短码负责记忆和传播，中文名负责理解。

## 4. 每周内容节奏

| 日期 | 内容 | 目标 |
|---|---|---|
| 周一 | 一张高压选择题 | 评论和收藏 |
| 周二 | 4 种结果卡对照 | 用户认领身份 |
| 周三 | 评论区高频答案解析 | 二次分发 |
| 周四 | 情侣/闺蜜互测题 | @朋友和转发 |
| 周五 | “3 个测试拼出你的组合人格” | 提高万能卡价值感 |
| 周六 | 本周最有分歧的一题 | 复用优质题目 |
| 周日 | 下周新题投票 | 收集真实选题反馈 |

同一道好题至少拆成四种内容：选择题、不同人格怎么选、结果卡、评论区解析。不要每天重新发明一整套测试。

## 5. 卡密与订单台账

不要把 D1 的技术状态和订单台账的交付状态混成一个字段。

D1 是兑换真相源，沿用现有三个技术状态：

- `active`：允许首次兑换。它可能“库存未发”，也可能“已经发给买家但尚未兑换”。
- `used`：已经首次兑换，不可再次兑换。
- `disabled`：人工禁用，不可兑换。

订单台账单独记录四个业务状态：

- `inventory`：已生成、未绑定订单。
- `issued`：已绑定并交付订单，尚未确认兑换。
- `redeemed`：D1 已显示 `used`。
- `revoked`：D1 已改成 `disabled`，并记录原因。

对应关系：`inventory/issued → active`，`redeemed → used`，`revoked → disabled`。不要尝试把 D1 状态直接写成 `issued` 或 `revoked`，现有数据库不接受这两个值。

每次发码至少记录：

| 字段 | 用途 |
|---|---|
| batch_id | 追踪生成批次 |
| order_no | 对应小红书订单 |
| card_key | 交付的兑换码 |
| business_status | 订单交付状态 |
| d1_status | D1 技术状态 |
| issued_at | 发码时间 |
| redeemed_at | 首次激活时间 |
| support_note | 补发、退款或异常说明 |

从 [`CARD_LEDGER_TEMPLATE.csv`](./CARD_LEDGER_TEMPLATE.csv) 复制一个私有台账开始使用；模板只保留表头，实际订单号和完整卡密不得填写回代码仓库。私有台账是业务状态的唯一真相源，仅店主和售后账号可访问。

管理规则：

1. 一笔订单只发一个未使用码。
2. 发码后立即把订单号和卡密绑定，禁止从聊天记录临时查找。
3. 已兑换码不重复销售。
4. 用户反馈失效时先查兑换状态和访问浏览器，不直接盲目补码。
5. 确认交付故障可补发时，作废旧码并记录原因。
6. 每周核对 `已付款订单数 = 已发码数 + 待处理数`。

### 标准批次流程

批次统一命名为 `xhs-YYYYMMDD-序号`，例如 `xhs-20260715-01`。每次只生成足够 1—2 周销售的数量，避免大量明文卡密长期散落。

```bash
cd /mnt/d/biancheng/qian/worker
node scripts/generate-cardkeys.js --count 100 --batch xhs-20260715-01 --prefix XHS
./node_modules/.bin/wrangler d1 execute card_keys_db --remote --file=../z-rubbish/card-batches/xhs-20260715-01.sql
```

本机当前 WSL 中没有可用的 Linux 版 Wrangler，PATH 里命中的是 Windows 版本；因此首次远端操作前必须先在 `worker/` 内安装 WSL 本地依赖，再确认平台：

```bash
cd /mnt/d/biancheng/qian/worker
test -f package.json || npm init -y
npm install --save-dev wrangler
node -p "process.platform"                 # 必须输出 linux
./node_modules/.bin/wrangler --version      # 必须能正常输出版本
```

若上述预检不通过，不要改用 Windows Wrangler 混跑，也不要继续远端导入。

导入后立即核对批次，不以生成脚本的输出代替远端入库结果：

```bash
./node_modules/.bin/wrangler d1 execute card_keys_db --remote --command="SELECT batch_id, status, COUNT(*) AS count FROM card_keys WHERE batch_id='xhs-20260715-01' GROUP BY batch_id, status;"
```

售后禁用某个尚未兑换的码时，先确认订单，再执行参数已替换的更新语句；不要批量复制粘贴未核对的卡密：

```bash
./node_modules/.bin/wrangler d1 execute card_keys_db --remote --command="UPDATE card_keys SET status='disabled', updated_at=datetime('now') WHERE code='XHS-XXXX-XXXX-XXXX' AND status='active';"
```

安全规则：

1. 新生成批次统一落在已忽略的 `z-rubbish/card-batches/`；TXT 和导入 SQL 都含完整卡密，只保存在受控本机，不要发到群聊、网盘公开链接或截图里。
2. 每次只从 `inventory` 取一个码交付，交付后立刻绑定订单并改成 `issued`。
3. D1 只记录兑换，订单号和客服备注保存在私有台账；当前 Worker 不提供后台管理接口。
4. 发给用户的是单个卡密和使用说明，不发送整个批次文件。
5. 批次完全售出并完成售后窗口后，将交付文件移出日常工作目录归档；不要把它复制回 Worker 源码目录。
6. 现有 `worker/seeds/` 中可能有仍在使用的历史批次，本轮不自动移动或删除；核对远端状态与订单后再人工归档。

### 数据最小化与门禁边界

当前 Worker 在兑换时会保存完整 User-Agent 和无盐 SHA-256 IP 哈希，并在兑换日志中重复记录。它们只能用于短期故障排查和滥用排查，不用于画像、营销或与买家身份拼接；仅店铺运营者可访问，不导出给无关人员。

在未加入自动保留策略前，每月人工清理 30 天前的标识数据，同时保留不含设备标识的卡密状态与兑换时间：

```bash
./node_modules/.bin/wrangler d1 execute card_keys_db --remote --command="DELETE FROM redemption_logs WHERE created_at < datetime('now','-30 day'); UPDATE card_keys SET used_user_agent=NULL, used_ip_hash=NULL WHERE used_at < datetime('now','-30 day');"
```

执行清理前先导出行数统计并确认数据库名；本手册只给出操作模板，本轮没有对远端执行任何命令。

当前权益门禁是前端 Cookie/localStorage 的 MVP，不是账号制强鉴权：技术上可被手动绕过，也不能在清数据后恢复。商品文案必须始终带上“同一浏览器、换设备或清数据可能无法恢复”，不要宣传为永久账号权益或防共享授权。当前 Worker 的 CORS 为 `*`，在销量扩大前应另立一次 Worker 安全改造，评估来源白名单、限速与更少的设备数据采集；这会影响接口和预览环境，必须单独测试后再部署。

## 6. 客服标准话术

购买前：

> 这是 1.9 元的 15 测万能卡。每码仅首次激活一次，激活后同一浏览器可查看商品页列明的 15 项深度报告。换设备、换浏览器或清理数据后可能无法恢复，请在常用浏览器完成并保存结果图。

兑换步骤：

> 打开任一测试，完成后先看免费结果；点击“输入兑换码解锁”，粘贴卡密即可。成功后同一浏览器里的其他测试深度报告也会解锁。

无法查看：

> 请先确认仍在首次激活时使用的浏览器和设备，并避免无痕模式。把报错提示和当前测试名称发来，我会先核对卡密状态；确认是交付故障后再处理补发或退款。

不要使用“虚拟商品一律不退”拒绝所有问题。兑换码无效、服务未交付或商品描述不符仍需按实际情况处理。

### 小红书履约与自动化

当前优先使用平台官方能力，不部署模拟点击、抓取私信或自动登录的小红书机器人：这类机器人会带来账号风控、误发卡密和订单错绑，1.9 元客单也不足以覆盖维护成本。

推荐分三阶段：

1. 日订单少于 20：官方客服快捷回复 + 私有卡密台账，付款后从 `inventory` 取一码，绑定订单后发给买家。
2. 日订单稳定超过 20，或人工履约超过 30 分钟：在千帆后台申请虚拟/服务商品自主发货。申请条件、类目和在售商品数量以后台当日展示为准；未获批前不绕过平台流程。
3. 官方自主发货可用后：只把“订单号→未使用卡密→交付状态”接入获批能力，保留失败重试、人工补单和日志脱敏；不让机器人直接操作 D1 全量库存。

店铺只保留一个主商品 `AI 趣味测试完整报告兑换码｜1.9元15测万能卡`。不要为了凑申请数量复制三个近似商品；3 个新增 H5 是测试入口，不等于 3 个店铺商品。

## 7. 每周数据看板

最少记录以下漏斗：

```text
笔记曝光
  → 商品页访问
    → 支付订单
      → 兑换成功
        → 首项深报查看
          → 第二项测试完成
            → 分享卡生成
```

核心指标：

- 商品点击率 = 商品页访问 / 笔记曝光。
- 下单转化率 = 支付订单 / 商品页访问。
- 兑换成功率 = 兑换成功 / 已发码订单。
- 跨测使用率 = 完成第二项测试的已兑换用户 / 兑换用户。
- 分享意愿 = 分享卡生成 / 完成测试。
- 售后率 = 需要人工处理的订单 / 支付订单。

没有真实数据时不展示“已测试人数”“超过全国多少人”或虚构好评。

当前可直接拿到的数据只有小红书曝光/点击/订单、订单台账，以及 D1 的首次兑换结果和首次兑换产品。现有前端没有跨测完成与分享事件上报，因此“跨测使用率、分享意愿”暂时只能留空，不能凭感觉填写。等自然成交稳定后，再单独评估是否增加最小化、匿名的事件统计；未增加前不把这两项当已具备的看板。

### 1.9 元商品的盈利纪律

这类低客单商品不能靠复杂促销赚钱，核心是自然流量、低售后和同一内容反复利用。统一用下面的式子看收益：

```text
周成交额 = 笔记曝光 × 商品点击率 × 下单转化率 × 1.9 元
周可支配收益 = 周成交额 - 平台实际费用 - 退款 - 补发与人工售后成本
```

- 不用“降到 0.9 元”解决点击低；点击低应先改首图、标题和选题。
- 不用增加多个 SKU 解决转化低；先把“1 张卡解锁 15 项深报”讲清楚。
- 单条笔记曝光高但商品点击低，说明内容有趣但商品承接弱。
- 点击高但下单低，优先检查商品主图、15 项清单、使用说明和售后边界。
- 下单后兑换失败多，先修交付和浏览器提示，暂停加流量。
- 在自然成交数据稳定前不投付费流量；1.9 元客单很容易被获客成本吃掉。
- 每周选出“成交最多的一道题”，下周做结果卡、朋友挑战、评论解析三个变体，降低内容生产成本。

## 8. 实验方法

每周只测试一个变量，至少观察 7 天：

- 首图：假设题 vs. 结果卡。
- 标题：身份认领 vs. 朋友挑战。
- CTA：先免费出结果 vs. 解锁完整报告。
- 推荐顺序：关系类优先 vs. 自我类优先。

保留曝光、点击、订单和分享四个结果，不用单条笔记的点赞数替代成交判断。表现好的题目进入常青题库，网络梗题设置季度复审日期。

## 9. 内容与合规红线

- 统一写明“AI 趣味生成，仅供娱乐参考”。
- 不称专业心理诊断、医学评估或权威人格量表。
- 不写“测他还爱不爱你、复合概率、正缘、真实心理、保证准确”。
- 不使用性别羞辱、疾病梗、人格鄙视链、身材羞辱和攻击性结果名。
- 双人测试不能在另一方未参与时判断对方忠诚度或真实意图。
- 不强制分享后才能查看免费结果。
- 不伪造倒计时、库存、样本量、准确率或全国排名。
- 上线前在小红书千帆后台核对当前虚拟/服务类商品类目、履约和售后规则。

## 10. 维护节奏

- 每周：复盘漏斗、补充卡密库存、挑选一题复用。
- 每月：淘汰低点击题目，检查 15 项导流链接和兑换流程。
- 每季度：更新 20% 社交语境题和 10% 梗题，保留 70% 常青题。
- 每次改题：同时记录题目版本、结果模型版本和发布日期。
- 每次部署前：完成 15 项构建、兑换回归、分享卡检查和移动端检查。
